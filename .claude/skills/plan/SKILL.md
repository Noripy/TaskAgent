# 実装計画を立てる

引数: やりたいことの一言（例: `/plan メモを検索できるようにする`）

コードを書く前に、**下の型で計画を書いて提示する**。調べる必要があるときは先に読む（`grep` や既存ドキュメント）。
計画は会話に出す。長い設計判断になったものだけ `docs/design-docs/adr/` に残す。

## 計画の型（この見出しをそのまま使う）

### なぜ必要か
- 誰のどの困りごとが、いまどう解決されていないか。1〜3 行。
- 迷ったら `docs/product/persona.md` に照らす。「最初の一歩が小さくなるか」で答える。
- 機能追加の依頼でも、**やらない理由が見つかったらここに書く**（YAGNI）。

### 影響範囲
- 触るファイルを層ごとに挙げる（`src/core` / `src/server` / `src/client` / `migrations` / `docs`）。
- 既存の振る舞いを変えるか、足すだけか。壊れうる箇所を名指しする。
- ドキュメント（構成図・ER・フロー）の更新が要るかを `/design-sync` の対応表で確認する。

### 案（最小案 + 代替案を 2 つ以上）

| | 最小工数案 | 代替案 A | 代替案 B |
|---|---|---|---|
| やること | | | |
| メリット | | | |
| デメリット | | | |
| 工数感 | | | |

**採用案とその理由**を 1〜2 行で書く。「最小案で足りるならそれを選ぶ」が既定（KISS）。

### テスト方針
- どの層にどんなテストを書くか（`test/core` / `test/unit` / `test/workers`）。
- 最初に書く失敗テスト（Red）を 1 つ、具体的に書く。

### 確認方法
- 人が動きを見る手順（`pnpm docker:dev` で何をどう操作すると分かるか）。
- 機械で確かめる手順（`pnpm verify` に加えて必要なものがあれば）。

## 提示したあと

1. 計画を出す。**危険・不可逆・スコープが変わる判断があるときだけ、承認を待つ**。
2. それ以外は `/tdd` に進む（計画はそのまま TDD の Plan 段になる）。
3. 実装中に計画とズレたら、ズレた事実と理由を 1 行で伝える。黙って変えない。

## やらないこと

- 計画を書かずに実装を始める
- 代替案を 1 つも挙げずに「これでいきます」と言う
- 計画に書いていないものをついでに直す（別サイクルにする）
